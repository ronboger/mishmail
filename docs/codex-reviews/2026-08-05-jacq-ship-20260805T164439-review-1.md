# Review: Priority window setting (recency cap for starred/IMPORTANT hoist)

Task: "now it shows too many starred/priority emails. there should probably
be a way for a user to set this."

## Design decision

After ae78d2a made manual stars always hoist, months of accumulated stars
can bloat the pinned Priority section. The ergonomic control is a recency
window, not a count cap: "Only pin recent mail" — Last 3 / 7 / 14 / 30 days
/ All starred, default 7. Older starred/IMPORTANT threads stay in their
chronological date sections. VIP pins are exempt (vipAlwaysPins path — VIPs
are people, not backlog). Hidden-category semantics from ae78d2a unchanged.

## Change (commit 8083035)

- PrioritySplit: `cutoff(days:now:)` helper (<=0 → nil); qualifies/partition
  gain `newerThan: Date?`; star and IMPORTANT qualification additionally
  require `lastDate >= newerThan`; VIP/.off/.vips ignore it. Docs updated.
- SettingsView: "Only pin recent mail" Picker inside the Priority section
  (shown for .starred/.starredImportant), @AppStorage("priorityWindowDays")
  default 7; footer sentence added.
- ThreadListView: reads the setting, passes cutoff in recomputeLayout, new
  onChange(of: priorityWindowDays).
- MailStore: advanceForPriorityUnstar reads priorityWindowDays from
  UserDefaults (absent → 7, mirroring the vipAlwaysPins pattern) and passes
  the cutoff through PrioritySectionAdvance.idsLeavingSection (new
  defaulted param). captureStarNavAnchor now skips the anchor/scroll hold
  when the focused thread, once starred, would not qualify under the
  current mode + window + VIP settings — starring an old thread no longer
  re-partitions, so a viewport hold would be wrong.
